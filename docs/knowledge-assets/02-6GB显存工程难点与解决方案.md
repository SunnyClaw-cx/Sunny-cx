# 02 · 6GB 显存工程难点与解决方案

> 场景：**GTX 1060 6GB / sm_61** 单卡训练 **524M（0.5B）** 模型。
> 全部结论来自本项目真机实测；每个问题都给出「症状 → 根因 → 修法 → 验证」四段。
> 本文是本项目**最有复用价值**的一份——四个坑有三个会「静默失败」。

---

## 显存账本：为什么 6GB 能训 0.5B（先算清再动手）

**训练态显存 ≈ 20 bytes / param**（朴素 AdamW 口径）：

| 项 | 字节/参数 | 524M 时 |
|---|---|---|
| fp16 权重 | 2 | 0.98 GiB |
| fp16 梯度 | 2 | 0.98 GiB |
| AdamW fp32 的一阶/二阶矩 m,v | 16 | 5.86 GiB（❌ 装不下） |

> 纯 AdamW 全参训练 0.5B **需要 ≥8.8 GB**，6GB 卡物理装不下。

**破局三件套**：
1. **8-bit AdamW**（bitsandbytes）→ 优化器状态 16B → **2B**，省 4.1 GiB
2. **权重/梯度 fp16 驻留** → 权重+梯度 4B → 省 2.1 GiB
3. **梯度检查点** → 激活内存 0.576 → 0.378 GB

**最终实测构成（3.17 / 6.00 GB）**：
```
fp16 权重 0.98  +  gck 激活 ≈0.24  +  8bit Adam 状态 0.98  +  梯度 0.98  =  3.17 GB
```

> ⚠ **3.17GB 不是"没用满"，那 2.8GB 是必须留的安全边际。**
> Windows + 桌面合成 + 6GB 卡：**绝不能把显存压到 5.5GB（85~90%）**，
> 碎片化 + 桌面占用必然 OOM。留边际是工程必需，不是浪费。

## P0-1 · 权重驻留精度决定 OOM 与否（**生死线**）

### 症状
6GB 卡上刚起步就 OOM，报在第一次 embedding 查表。

### 根因
`model.to(device)` **默认保持 fp32** → 524M × 4B = **2.10 GiB 权重**，
梯度同量级 → 合计约 4.2 GiB，还没算激活就爆了。

### 修法
```python
# ❌ 默认 fp32 驻留
model.to(device)

# ✅ 显式转 fp16
model.to(device=device, dtype=torch.float16)   # 权重 0.98 GiB
```

### 验证
显存峰值从 OOM → **3.19 / 6.00 GB**。

> **这是 num_params × 4 vs × 2 的差别，不是"优化技巧"，是能不能跑起来的分界。**

## P0-2 · fp16 权重与 torch GradScaler 不兼容

### 症状
启动即抛：
```
ValueError: Attempting to unscale FP16 gradients.
```

### 根因
`GradScaler.unscale_()` 会**校验梯度 dtype**；
而权重是 fp16 时，梯度也是 fp16，直接被拒。

### 修法：自写 `StaticScaler`（固定系数 S=1024，2 的幂避免舍入误差）
```
forward : loss' = loss · S
backward: grad' = grad · S      ← 把 fp16 下溢的小梯度抬进可表示范围
update  : grad  = grad' / S     ← 还原真实量级后再 clip / step
```
> 用 2 的幂（1024）是为了除法变成指数位减法，**无舍入误差**。

## P0-3 · fp16 梯度裁剪会「静默清零梯度」（**最阴险**）

### 症状
**loss 突然卡住不动**，但**没有任何报错**。训练看起来"正常在跑"。

### 根因
`torch.nn.utils.clip_grad_norm_` 在**梯度自身精度**下求范数：
fp16 下 `grad.pow(2)` 在 |grad| > ~256 时**上溢为 inf** →
总范数变 inf → 裁剪系数退化为 **0** → **梯度被整体清零**。

### 修法：自写 `clip_grad_norm_safe()`，统一在 **fp32** 下累加范数
```python
# 关键：先转 fp32 再 pow(2) 累加
total = torch.zeros((), device=device, dtype=torch.float32)
for p in params:
    if p.grad is not None:
        total += p.grad.detach().float().pow(2).sum()
norm = total.sqrt()
```

### 验证
正式训练裁剪后 gnorm 稳定 **0.57~0.64**，从未出现"loss 卡住"。

> **排查口诀**：loss 不动 + 无报错 → 优先怀疑**梯度被静默清零**，而不是数据或 lr。

## P0-4 · RoPE 表精度提升会拖垮整条注意力路径

### 症状
混合精度"开了但没效果"，显存也没省。

### 根因
cos/sin 表以 fp32 预计算（角度精度需要），
若直接与 **fp16 的 q** 相乘 → **类型提升把整条注意力抬回 fp32**，
既费显存又失去混合精度意义。

### 修法
`apply_rope()` 内**按 q 的 dtype 转换** cos/sin：
```python
cos = cos.to(q.dtype); sin = sin.to(q.dtype)
```

## 附带 · 日志块缓冲导致"训练无输出"

**症状**：日志文件长时间不更新，看起来像卡死。
**根因**：stdout 重定向到文件时 Python 默认 **4~8KB 块缓冲**。
**修法**：`sys.stdout.reconfigure(line_buffering=True)` + 用 `python -u` 启动。

## 四个坑的共性（值得写成检查表）

| 坑 | 是否报错 | 危险等级 |
|---|---|---|
| 权重 fp32 驻留 OOM | 报错（OOM） | 中（能看见） |
| GradScaler 不兼容 | **报错** | 低（能看见） |
| **fp16 裁剪清零梯度** | **不报错** | **极高** |
| RoPE 类型提升 | **不报错** | 中（静默降效） |
| 日志块缓冲 | **不报错** | 低（形成假象） |

> **工程铁律**：混合精度下，凡是"安静地不工作"的东西，
> 都要**主动加断言探针**（打印 dtype / grad norm / 范数是否有限），
> 不能指望它报错。
