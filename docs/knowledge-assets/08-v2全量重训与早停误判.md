# 08 · v2 全量重训与早停误判

> 本篇推翻并修正了 03 / 05 / 07 三篇里关于「预训练已到顶」的全部结论。
> 所有数字来自 2026-10-17 ~ 10-18 真机实测，口径随数字一同标注。

## 一、先说结论

| 原判断 | 现判断 | 依据 |
|---|---|---|
| 预训练已到顶，5600 步早停合理 | **早停被误触发，4600 之后 1000 步是白跑的** | 1200 条大样本评测：latest@5600 优于 best@4600 |
| 语料只有 1,018,615 条，训完就没了 | **语料清洗有 bug，丢掉了 2,672 万字符真实内容** | 字符级漏斗对账 + 端到端 A/B |
| 被删数据都是脏数据 | **被删部分 58.2% 是正常医学论述** | 抽样复核 2,612 万字 |
| 续训用 `--from_resume` 就行 | **要跑满新语料必须用 `--from_weight` 热启动** | resume 会继承 step=5600，跳过前 43% |

## 二、早停误触发：验证集抽样缺陷

### 2·1 症状

v1 训练在 12:07:35 自动停止，`patience=5` 用尽，best val 3.8995 @ step 4600。
表面上是一次正常的早停，但用户提出质疑：「我有很多本书的数据，这才训练到哪里就满了」——这个质疑是对的。

### 2·2 根因

`dataset.py` 的 `ValSubset` 用**硬编码步长**抽样：

```python
if i % 2000 == 0:      # 写死的 2000
    take(line)
```

验证集 `tcm_classics_pretrain.val.jsonl` 只有 53,705 行，`i % 2000 == 0` 只能抽到 **27 条**。
不足 `val_samples=64` 时，补齐逻辑从**文件头**顺序抓 37 条 → 最终 64 条里
**59% 来自两本书**（炙膏肓腧穴法 31% + 疝氣證治論 28%），全集只覆盖 25 本书。

一个 64 条、59% 集中在两本书的验证集，无法代表 2,043 本古籍的分布。loss 在 4600 之后不再改善，
是这两本书的 loss 不再改善，不是模型不再进步。

### 2·3 决定性对照（`scripts/eval_compare.py`）

| 评测口径 | best@4600 | latest@5600 | 差值 | 谁更优 |
|---|---|---|---|---|
| **大样本 1200 条（无偏）** | 3.5269（ppl 34.02） | **3.4406（ppl 31.21）** | **−0.0863** | **latest@5600** |
| 官方 64 条（有偏） | 3.8992 | 3.9056 | +0.0064 | best@4600 |

**两个口径给出完全相反的排序。** 小样本口径的噪声（7.4k token）盖过了真实信号（0.086 的差距）。

### 2·4 修法与纪律

- `ValSubset` 改为**步长自适应**：新增 `_count_lines` 先数总行数，按 `total // val_samples` 算步长，
  顺序补齐仅作兜底
- 训练参数：`--val_samples 400`（原 64）、`--patience 20`（原 5）
- **纪律：`val_samples < 200` 时早停结论不可信。** 这个阈值不是拍脑袋——
  64 条 ≈ 7.4k token 的评测标准差，已经大于模型在 1000 步内的真实增益

## 三、语料漏斗：2.3863 亿 → 1.6584 亿，少了 25.94%

### 3·1 逐级对账（`tcm-llm/scripts/diag_funnel.py`）

| 环节 | 剩余字符 | 本环节减少 |
|---|---|---|
| 原始语料 | 2.3863 亿 | — |
| 进入过滤链 | 1.6584 亿 | **−7,279 万（−30.5%）** |
| ├ 正文保留 | 13,832.5 万 | |
| ├ 目录类删除 | −974.2 万 | |
| ├ 本草序例删除 | −999.6 万 | |
| ├ 剧毒中药相关删除 | −545.2 万 | |
| ├ 剂量句式删除 | −66.5 万 | |
| ├ 序跋删除 | −25.9 万 | |
| ├ 其他规则删除 | −0.8 万 | |
| └ **长段切句后碎片丢弃** | **−2,672 万（681,372 片）** | **真内容，不是脏数据** |

整链自洽：13,832.5 + 974.2 + 999.6 + 545.2 + 66.5 + 25.9 + 0.8 + 139.4 ≈ 16,584.1 万。

### 3·2 碎片 bug（已修）

`build_dataset.py` 的 `split_paragraphs` 把长段落切成句子后，**凡不足 40 字的片段直接丢弃**。
古籍条文本身很短（「太阳病，头痛发热，身疼腰痛」= 14 字），这些被丢的是**真条文**，不是残渣。

修法：改为**贪心累积**——相邻短句攒够 40 字合成一个样本，尾片并回同段。
验证：147,995 样本 0 条越界，最长 1,200；端到端字符量 **+12.99%**。

> ⚠ 教训：维修前预估能救回 1,870 万字符，实测端到端只有 **+1,621 万**（过滤链又删了 1,051 万）。
> **今后凡"修复可救回 X 万"，必须标「上限，实测可能低 10~40%」。**

### 3·3 误杀率：被删的 58.2% 是好数据

对被删的 2,612 万字符抽样复核：**1,521 万（58.2%）是正常医学论述**。五条误杀机制：

| 机制 | 说明 |
|---|---|
| 碎片 bug | 短条文被当成残渣丢弃（见 3·2） |
| `is_toc_like` 顿号 ≥8 | 方剂组成本身就是顿号串（「人参、白术、茯苓、甘草、当归、川芎……」）→ 被误判为目录 |
| `TOXIC_HERBS` 单词命中 | 含剧毒中药名的**整段**删除，而正确做法是只删该方，不是删整段论述 |
| `is_herb_entry` 强求标记 | 要求特定格式标记，格式不符的正常本草条目被漏判 |
| 「余谓」判序跋 | 「余谓」在医籍正文中极常见，被当成序跋特征 |

### 3·4 重建后的 v2 语料

|---|---|---|
| 条数 | 1,018,615 | **1,222,973** |
| 字符 | 1.181 亿 | **1.4096 亿（+19.4%）** |
| token | 0.945 亿 | **≈1.128 亿** |

### 3·5 隐蔽陷阱：繁体不转 → 黑名单失效

笈成 1,254 本中 **98.2% 是繁体**。预处理后仅 3.45% 残留，说明繁简转换曾经生效；
但重建语料时当前 venv **没有 opencc**，重跑会绕过全部简体关键词黑名单，**过滤与去重同时失效**。

已装 `opencc-python-reimplemented` 并验证：98.15% → **0.00%**。
**纪律：重跑任何语料脚本前，先确认 `import opencc` 可用。**

## 四、热启动 ≠ 续训

要「把新语料全部训一遍」，起点必须归零，但参数可以继承。

| | `--from_resume` | `--from_weight`（热启动） |
|---|---|---|
| 搬什么 | model + optimizer + scaler + **step** + early_stop | **只搬参数** |
| step 起点 | 5600 → **跳过新语料前 5600 步（43%）** | 0 → 新语料 **100% 覆盖** |
| early_stop | 继承 `bad_count=5` → **可能启动即停** | 全新计数 |
| 适用 | 同语料中断续跑 | 换语料重训 / 扩语料 |

`train.py` 原逻辑 `if stage == "sft" and from_weight` 把热启动限制在 SFT，
已改为 `if from_weight`，预训练同样可用。

### 4·1 tied embedding 的提取陷阱

`tie_word_embeddings=True` 使 `lm_head` 与 `embed_tokens` 指向**同一个 Parameter**。
提取纯权重时若用 `.clone()`，会破坏 storage 共享：

- 文件多出 14 MB
- 参数量算成 531,506,304（真值 524,133,504）
- 载回后 tied 关系丢失，等于换了模型结构

**正确做法：只搬引用，不 clone。**

热启动源选 v1 的 `latest@5600` 而非 `best@4600`（大样本 ppl **31.21 vs 34.02**）：
`checkpoints/sunnycx_0.5b_pretrain_warm5600.pth`，999.79 MB，291 张量，
载入 `missing=0 unexpected=0`。

## 五、v2 训练方案与实测

| 项 | 值 |
|---|---|
| 语料 | `tcm-llm/data/processed_v2/`，1.0824 亿 token |
| **1 轮** | **13,212 step**（batch 2 × seq 512 × accum 8 = 8,192 tok/step） |
| 纯训练 | 60.6 h（17.4 s/step 实测） |
| 验证 | 3.9 h（33 次 × 425 s，400 条/次） |
| 含休息 ×1.25 | **80.6 h ≈ 3.36 天** |
| 显存峰值 | 3.22 / 6.00 GB |
| 配置 | `epochs 1` / `val_interval 400` / `val_samples 400` / `patience 20` / `lr 2e-4` / `save_interval 100` |

`lr` 从 3e-4 降到 **2e-4**：热启动时参数已在较好的位置，用原学习率会把已有的下降冲掉。

### 5·1 启动

**用户双击 `scripts\start_training_v2.bat`**。逻辑：

```
存在 v2 检查点 → --from_resume（断点续训）
否则        → --from_weight checkpoints/sunnycx_0.5b_pretrain_warm5600.pth（热启动）
```

内置 `guard_single_instance.py` 防双开：判据必须同时满足
**命令行含 train.py** 且 **WorkingSetSize > 500 MB**
（venv 的 `python.exe` 是 11 MB 转发 shim，与真实训练进程命令行完全相同，只看命令行会误判）。

### 5·2 首步验证 = 热启动成功的证据

```
Epoch:[1/1](20/13212), loss: 3.2024, lr: 2.0e-05, gnorm: 0.609, elapsed: 5.8min, peak: 3.22/6.00GB
```

step 20 的 loss 是 **3.2024**，不是从零起跑的 5.2877 —— 这是权重真的被载入的直接证据。

## 六、复现清单

```bash
# 1. 确认环境（繁简转换是前置条件）
python -c "import opencc; print('ok')"

# 2. 重建语料（已做过，仅需重跑时使用）

# 3. 提取 tied 安全的热启动权重（不 clone）

```
