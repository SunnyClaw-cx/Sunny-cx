# 07 · 训练运维与排障手册

> 长跑训练（本项目 2 epoch 合计 4~6 天）的**存活、续训、排障**全套经验。
> 每一条都是**真实事故**后的结论，不是预防性建议。

---

## 一、★ 最重要的运维约束：进程存活

### 事实：agent/自动化会话结束时，子进程会被清理

**实测证据**：2026-10-16 当天训练**中断两次**（一次停在 step 100，一次只到 step 3）。

### 五条脱离路径全部失败（均已实证）

| 方案 | 结果 |
|---|---|
| `DETACHED_PROCESS + CREATE_NEW_PROCESS_GROUP` | 探针无输出，进程消失 |
| `+ CREATE_BREAKAWAY_FROM_JOB` | **WinError 5 拒绝访问**（沙箱 job 不允许 breakaway） |
| `cmd /c start /b` 中间层 | 探针无输出 |
| WMI `Win32_Process.Create` | **被安全策略拦截**（等同 Start-Process） |
| `schtasks` 计划任务 | **程序黑名单拦截** |

**反证**：探针脚本本身正常（前台跑持续写 tick）→ 排除脚本问题，确认是**进程被清理**。

> 但训练进程能**跨多次工具调用存活** → 被清理的是**会话级**，不是调用级。

### ✅ 唯一可行方案：独立窗口启动器

交付 `scripts/start_training_window.bat`，用户**双击**即在自己控制台跑，彻底脱离 agent 会话。

- 内含单实例守卫 `scripts/guard_single_instance.py`
- **守卫为什么单独写成 .py**：在 .bat 里内联 PowerShell + 多层引号转义，
  cmd.exe 会吞掉反斜杠 → 条件恒假 → **守卫静默失效**（实测复现过）
- **守卫判据细节**：不能只按 `CommandLine like '*train.py*'` 计数 ——
  venv 的 `python.exe` 是个 **11MB 转发 shim**，与真实训练进程（1.6GB）**命令行完全相同**
  → 故加 **`WorkingSetSize > 500MB`** 阈值。实测 count=1（正确只认真实训练进程）

> 若必须在会话内启动，唯一可行是 `run_in_background: true` 后台任务（有 task_id，跨工具调用存活）。
> `nohup cmd //c xxx.bat &` 会被沙箱随命令结束一起清理（进程 10 分钟内全部消失）。

## 二、★「改了代码不生效」的根本原因

### 症状
改了 `cloud.py`，大屏仍是旧行为。

### 根因
**训练进程启动时间早于代码修改时间。**
Python 在 import 时把模块编译进内存，**改磁盘上的 `.py` 对运行中的进程无效**。

> **源码改动要生效 → 必须重启训练进程。这是本项目最重要的一条运维约束。**

### 无损重启流程（可复用）
1. **等存盘点**：`save_interval=100` → 等到 checkpoint 推进到整百（最多等约 5 分钟），
   避免白跑最多 99 步
2. `Stop-Process -Id <PID> -Force`
   （判据：`CommandLine like '*train.py*' AND WorkingSetSize>500MB`，排除 11MB venv shim）
3. **必须用后台任务启动**（见上一节）
4. 验证续训：日志应出现
   `[resume] 恢复早停状态：best_val=... @ step ...`，且从 **checkpoint+1** 继续
   （先自增再消费，无重叠）

## 三、OOM 排查（Windows 多进程 DataLoader 特有问题）

### 症状
训练跑满 1h13m 后崩溃：
```
memory allocation of 802832 bytes failed
RuntimeError: DataLoader worker (pid(s) 48204) exited unexpectedly
  at evaluate() -> val_loader
```

### ★ 决定性判据：报错字节数
**仅 802KB（<1MB）**。显存不足会报 **GB 级 + `CUDA out of memory`**。
**连 1MB 都分配失败 = Windows 系统级 commit 内存枯竭**，不是显存问题。

### 根因
| 项 | 值 |
|---|---|
| train num_workers | 4（常驻） |
| val num_workers | 2（**非持久，每次验证重建**） |
| 本次验证次数 | **37 次** → **74 次 spawn/join** |
| 系统基线占用 | 9.4 GB（物理 16GB / 提交上限 28.5GB） |

Windows **无 `fork()`**，每个 worker 重新起解释器并 **import 整个 torch 栈（300~500MB）**；
torch 2.6 反复 spawn/join 时**句柄与共享内存信号量不立刻回收** → 逐次累积 → 触穿 commit。

### 修复（4 处，缺一不可）
1. **val_loader → `num_workers=0, pin_memory=False`**（最关键）
   验证只跑前 40 batch（160 条），主进程内 <2s，**无需多进程** → 消灭 74 次 spawn
2. train `num_workers` 4 → 2（默认值 + 启动脚本 3 处显式传参**都要改**）
3. `evaluate()` 末尾加 `gc.collect()`
4. SFT 训练器同缺陷一并修复

> ⚠ **教训：显式传参会覆盖默认值。只改默认值不改启动脚本 = 修复不生效。**

### 验证（真机，非"应该没问题"）
| 判据 | 结果 |
|---|---|
| python 进程数 | 恒定 **6**（修复前反复抖动） |
| 提交内存 | 21778~22307 MB 窄幅波动，**非单调上涨** |
| 是否越过崩溃点 | ✅ 成功越过 step 19000 |

## 四、长跑保护：被动熔断 + 主动节律（两个独立机制）

| | `thermal.py` 温度熔断（被动） | `rest.py` 节律休息（主动） |
|---|---|---|
| 触发 | 温度 ≥82℃ 持续 20s，或驱动热降频 | **连续训练满 2 小时**（与温度无关） |
| 恢复 | 降到 ≤74℃ | 休满 **30 分钟** |
| 性质 | 异常兜底（真越界才停） | **节律轮换（到点就休）** |
| 实测 | **长跑从未触发**（24.8h 峰值 **81℃**，距 82℃ 仅 1℃） | 每 ~415 步触发一次 |

**两者都在 `optimizer.step()` 之后的干净边界暂停**：
梯度已清零、参数已落地，恢复时**直接继续，不需重放任何 step**。

### ★ 三个关键正确性点（改这块必查）
1. **休息时长必须从训练耗时扣除**：`t0 += time.time() - _rs`
   不扣 → elapsed 虚高、ETA 偏长；更糟的是**累计训练时长含休息 → 触发越来越频繁（正反馈失控）**
2. **`wait_rest()` 内必须重置 `self._last_tick = None`**
   否则下次 `guard()` 的 `now - last_tick` 会把 30 分钟休息算成训练时间
3. **累计状态落盘** `checkpoints/<save_weight>_reststate.json`
   续训/重启不重置，否则**反复重启即可绕过保护**

### 验证
- 单元测试（假时钟 + 假睡眠）**8/8 断言通过**：每 **415 步**触发（415×17.4s≈2.00h），
  休息精确 1800s，跨进程重启恢复 count=2/total=3600 ✅
- 端到端真实跑通：step 2 触发 → 暂停 → 休息 → 自动恢复 → 继续 step 3 ✅

## 五、大屏推送链路排障

### 5.1 「Δ权重」恒为 `—` → drift 死值

**根因（实测复现）**：`snapshot_weights` 与 `weight_drift` **设备不一致**。
- `train.py` 在 `model.to(cuda, fp16)` **之前**调 `snapshot_weights` → 快照是 **CPU/fp32**
- `weight_drift` 在训练循环里调用 → 权重已 **cuda:0/fp16**
- 相减 → `RuntimeError: Expected all tensors to be on the same device`
  → 被裸 `except` 吞掉 → 返回 None

**三处修复**：
1. 快照固定到 CPU/fp32：`p.detach().to("cpu", torch.float32).clone()`
   ⚠ **不能改 fp16 省内存**：真实漂移仅 2.8e-6，而 fp16 对 ~N(0,0.02) 权重的
   量化误差 ~1e-5 —— **比被测信号还大**
2. **逐层抽样代替"前 40 个张量"**：32 层模型有 290 个参数张量，
   按名字顺序前 40 个只覆盖 layer 0~4，**后 27 层完全没被观测**
   → 改按 `layers.(\d+)` 分组，每层取 attn/mlp/norm 各一个
3. 层数上限 16（全 32 层 ×3 类 = 703MB fp32 太大）→ 16 层等距抽样 / 50 张量 / 366MB

### 5.2 「VAL ×288」虚报（实际只验证 16 次）

**根因链**：
1. `parse_line` 给**每个 step** 都挂 `val_loss`（沿用最近值供顶栏显示）→ 每点都带 val
2. 推送层照单全收
3. 续训从 checkpoint 重放已训 step → **同一 step 出现两次**

**三层修复（缺一不可）**：
- **数据层**：新增 `val_at_step` —— 标明该 val **测于哪一步**
- **推送层**：只有 `val_at_step == 当前步` 才记 val；`_hist_put()` 按步号去重
- **展示层**：按步号间隔（<100 视为沿用点）+ `seen` 集合双重去重
  → **展示层是即时兜底**：即使云端残留脏数据，大屏也不会虚报

**验证**：真实 val 点 **288 → 17**，步号均为 200 整数倍。

## 六、探针脚本踩坑

### 6.1 同时加载多个检查点 → SegFault(139)
**症状**：脚本崩在加载阶段。
**根因**：同时 load best（1GB）+ latest（2.1GB）+ 模型 → RAM 被训练进程占满。
**修法**：**逐个加载，取完子集立刻 `del` + `gc.collect()`**。

### 6.2 张量计数口径
- 检查点含 **291** 张量（含 `lm_head.weight`）
- `named_parameters()` 因 **tied 只列 290**
- → 以 **`checkpoint ∩ named_parameters`** 为口径

### 6.3 复算脚本 RNG 错位（差 5 倍！）
**症状**：独立复算初始化权重得 117.6%，云端实测 22.4%，**差 5 倍**。
**根因**：`train.py` 的 `verify_param_count(cfg)` 会**先实例化一个完整模型**（消耗 RNG）再 `del`，
之后才建真正的 `model`。复算脚本漏了这次 RNG 消耗 → **随机流错位** → 重建的"初始化权重"不是那个。
**修法**：忠实复现那次 RNG 消耗后，`moved_pct=70.0%` / `tracked=50` **与云端精确一致**。

> **教训**：复算对不上时，**先怀疑复算脚本**，不要急着怀疑被测系统。

### 6.4 读日志前先按 mtime 排序
**症状**：读到旧日志，得出结论完全错误。
**根因**：日志文件名随启动脚本变（`pretrain_0.5b_run.log` vs `pretrain_0.5b_push.log`）。
→ **读日志前先按修改时间排序**。

## 七、`.bat` 文件编码铁律

| 规则 | 说明 |
|---|---|
| **必须 GBK + CRLF** | UTF-8 中文注释 → cmd.exe 按 GBK 读 → **混编解析崩坏** |
| **中文注释别写进 .bat** | 改成纯 ASCII 注释，零编码风险 |
| 修 .bat **不能用 Edit 工具** | 会破坏编码 → 用 Python 按 GBK+CRLF 字节级写回 |
| 警惕"危险续行" | 参数末行残留 `^` 会把下一行 `goto :eof` 吞进命令 |

本项目两条 bat 均遵守此规则：
`tcm-llm/scripts/run.bat`、`sunny-cx/scripts/run_pretrain.bat`。

## 十、一句话总结

> **长跑训练的敌人不是算力，是「静默失败」和「会话回收」。**
> 前者要靠**主动探针**发现（它不报错），
> 后者要靠**独立进程 + 断点续训 + 状态落盘**对抗（它不留痕）。
