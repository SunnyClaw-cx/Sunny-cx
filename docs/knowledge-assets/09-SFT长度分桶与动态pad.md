# 09 · SFT 长度分桶与动态 pad

> 本篇记录把一个 12.31 天的 SFT 计划压到 3.14 天的完整过程：
> 为什么不能打包、分桶怎么实现、语义怎么验证、真机基准怎么测、以及两次测错的教训。

## 一、问题：SFT 的 82% 算力在算 padding

SFT 语料长度分布（抽样实测）：

| 指标 | 值 |
|---|---|
| 均值 | 92.2 token |
| P50 | 77 token |
| P90 | 159 token |
| P99 | 249 token |
| max_seq_len | 512（固定 pad） |

按固定 pad 512 计算，**有效 token 占比只有 18.3%**，81.7% 的计算花在 pad 位上。

以 batch 2 × accum 8、67,596 个 optimizer step 折算：**12.31 天**。

## 二、为什么不能像预训练那样打包

预训练语料是 `{"text": ...}` 单段文本，打包时用 eos 把多条拼成一条长流再切块，
**每条 token 的 label 就是它的下一个 token**，结构无损。

SFT 语料是 `{"conversations": [...]}` 多轮对话，需要**逐 token 标记哪些位置算 loss**
（只有 assistant 段算，user 段和特殊 token 置 `-100`）。打包会把不同会话的轮次边界串在一起，
loss mask 语义被破坏 —— 模型会学着跨会话接话。

**所以 SFT 不能打包，但可以分桶。**

## 三、分桶 + 动态 pad 的实现

### 3·1 三个改动

| 位置 | 改动 |
|---|---|
| `SFTDataset.__init__` | 新增 `dynamic_pad=True`、`bucket_chunk=512` |
| `SFTDataset._build` | 样本本身**不再 pad 到 max_seq_len**，只截断 |
| `SFTDataset._emit_block` | 缓满 `bucket_chunk` 条后**按长度降序**排列再吐出 |
| `collate_pad` | pad 到**本 batch 最长**（向上取整到 8 的倍数） |

块内降序的作用：相邻 batch 的长度高度接近，pad 浪费趋近于零。

### 3·2 pad 位语义保持不变

这是整个改造的底线：pad 位必须仍然是 `label = -100`、`attention_mask = 0`。
只动 pad 的**长度**，不动 loss 与注意力的**掩码语义**。
一旦这里出错，训练会静默变差（loss 曲线看起来正常，模型实际学到 pad 位置输出）。

### 3·3 验证集必须保持固定 pad

`build_dataloaders` 里 SFT 的 val 分支**显式不走分桶**，仍是 `SFTDataset(dynamic_pad=False)`。

理由与 08 篇早停误判同源：val_loss 必须**同口径**才能跨 step 比较。
若训练用动态 pad、验证用固定 pad，两者计算的 pad 比例不同，loss 不可比 —— v1 的早停误判就是这么来的。

### 3·4 回退开关

`train.py` 新增 `--no_sft_bucket`（回到固定 pad）、`--sft_bucket_chunk`（默认 512）。
预训练路径**零改动**：`train_collate` 只在 `stage == "sft"` 分支被替换。

## 四、语义等价验证（`scripts/verify_sft_bucket.py`，纯 CPU）

在做任何计时之前，先证明「分桶不改变任何一条样本的语义」。比对内容：

| 比对项 | 结果 |
|---|---|
| 有效长度 | 120 条全部一致 |
| `input_ids` 真实段（去掉 pad） | 全部一致 |
| `labels`（含 -100 位置） | 全部一致 |
| `attention_mask` | 全部一致 |
| 新增断言：每条样本必须有 user 掩码位与 assistant 监督位 | 通过 |

只要这一项不通过，后面的加速数字都是拿质量换来的，不能报。

## 五、padding 账（1500 条，batch 2）

| 方案 | 有效 token | 实际计算 | 有效率 | 相对 |
|---|---|---|---|---|
| 固定 pad 512 | 140,679 | 768,000 | 18.3% | 1.00× |
| 动态 pad（不分桶） | 140,679 | 182,128 | 77.2% | 4.22× |
| **动态 pad + 分桶 512** | 142,603 | 148,512 | **96.0%** | **5.17×** |

注意有效 token 从 140,679 变成 142,603：因为不再 pad 到 512，原本会被截断的样本
（P99 = 249 < 512，实际不截断）完整保留，统计口径略有差异，属正常。

## 六、真机基准（`scripts/bench_sft_bucket.py`）

batch 2 × accum 8，覆盖整块 32 step，同一份模型权重、同一显存状态。

| 模式 | s/step | 有效 tok/s | 计算位置/s | 显存峰值 | 单轮 67,596 step |
|---|---|---|---|---|---|
| 固定 pad 512 | **15.73** | 94.9 | 520.8 | 3.22 GB | **12.31 天** |
| **分桶 + 动态 pad** | **4.01** | 371.8 | 386.6 | 3.16 GB | **3.14 天** |

**墙钟 3.92×。**

### 6·1 必须分开报的两个口径

| 口径 | 倍数 | 含义 |
|---|---|---|
| 算力级（有效 token 占比 18.3% → 96.0%） | **5.17×** | 理论节省的计算量 |
| **墙钟（s/step 15.73 → 4.01）** | **3.92×** | 用户真正拿到的时间 |

差值来自 **sm_61 上小张量效率更低**：计算位置/s 从 520.8 掉到 386.6（−25.8%）。
batch 变小、序列变短后，GPU 的并行度下降，单位算力的开销上升。

**只报 5.17× 是虚的。** 向用户汇报一律用 3.92×。

## 七、两次测量翻车（方法论教训）

### 7·1 第一次：改了签名没同步调用

`run_mode` 函数签名里漏了 `accum` 形参，调用处还在传 → `NameError`。
教训：改函数签名后必须全文件搜一遍调用点。

### 7·2 第二次：加速比虚高（这个更隐蔽）

第一版基准只跑开头 23 个 batch 就收工。但**分桶块内是按长度降序排列的**，
开头几个 batch 恰好是全块最长的样本 —— 拿它们代表整体，等于只测了最慢的那部分。

两次错误结果分别是 **2.09×** 和 **~5×**，都不是真值。

**修法**：`stride = chunk // (batch_size × accum)`，用等距抽样覆盖整个块；
跨块时跳过中间 batch（不计时，只为位移）。

### 7·3 可复用的基准纪律

1. 采样区间必须覆盖**完整的数据组织周期**（这里是 512 条一块）
2. 预热必须排除（首次 step 含 `cudaMalloc` 与 cuBLAS 句柄创建）
3. 计时前后都要 `torch.cuda.synchronize()`，否则测的是 CPU 排队时间
4. 同时记录**有效 token/s** 与**计算位置/s**，两者背离就是"省了计算但没省时间"
5. 显存峰值单独 reset 后再测，否则会继承上一模式的峰值

## 八、启动脚本

`scripts/_gen_bat_sft.py` 生成 `run_sft_v2.bat`（3,190 B）与 `start_sft_v2.bat`（1,453 B）。

**必须 GBK + CRLF**：用 Edit/Write 直接写会变成 UTF-8 + LF，cmd.exe 解析乱码。
生成后校验方法：

```python
b = open('scripts/run_sft_v2.bat', 'rb').read()
print(b.decode('gbk').splitlines()[0])   # 首行能正确解码 = 编码对
print(b.count(b'\r\n'), b.count(b'\n'))  # 两数相等 = CRLF 对
```

脚本自动选择初始权重，优先级：
`v2 best` → `v2 latest` → `v1 best` → `warm5600`。

学习率暂定 **1e-4**（未验证），首轮 SFT 跑出 val 曲线后须复核。
