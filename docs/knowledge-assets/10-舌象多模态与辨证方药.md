# 10 · 舌象多模态与辨证方药数据

> 本篇分两条线：**视觉侧**（舌象数据集接入）与**文本侧**（白话问诊 → 辨证 → 方药）。
> 两条线的共同前提都是「数据可得性」，而这是本项目最容易误判的地方。

## 一、需求与两条线的定位

用户诉求原话：「我白话文说我哪里不舒服，他给我中医推荐和药房推荐」，
后续追加「加入舌苔数据集图片，进行训练，理解白话文并找到对应的中医」。

拆开后是两个独立问题：

| 线 | 输入 | 输出 | 当前状态 |
|---|---|---|---|
| 视觉 | 舌象照片 | 舌象特征文本（「舌胖大、边有齿痕，苔白滑」） | 数据集已拿到，训练待 GPU 空出 |
| 文本 | 白话症状（可拼舌象描述） | 辨证 + 方剂 + 出处 + 免责 | 证型表已建，改写未开始 |

### 2·1 下载链路的三次失败与最终方案

| 尝试 | 结果 |
|---|---|
| `nohup curl ... &` | 下到 407 MB **进程被沙箱回收**（同 07 篇第八节） |
| `run_in_background` 单连接 | 速率约 800 KB/s → 2.34 GB 需 49 分钟 |
| 8 线程分段 | 早期 ~2 MB/s，中段掉到 409 KB/s，ETA 反而拉长 |
| **30 并发分段 + 断点续传** | 峰值 **5.4 MB/s** |

关键实测：**单连接被限速到 40 KB/s**，瓶颈在单连接配额而非总出口。
所以并发收益接近线性，但会被上游动态限流，越到后面越慢。
最终文件 2,344,175,413 B，与 Kaggle 声明字节数完全一致，CRC 全部通过。

## 三、TMC-Tongue 数据核查（三处必须先纠正）

数据集：`obaidulhaque/tmc-tongue-dataset`，即 Dryad `10.5061/dryad.1c59zw48r`（CC0）。

### 3·1 纠正一：不是 20 类，是 21 类

README 写「twenty categories, 0–19」，但实际标注是 **21 类（id 0–20）**，
README 漏写了 `piweitu`（脾胃区凸起）。

**以 COCO json 的 `categories` 为准**，不要以 README 或 `classes.txt` 为准。

### 3·2 纠正二：test 有 7 条越界标注

`test.json` 里有 **7 条 `category_id = 21`** 的标注（合法范围只到 20），
全部集中在同一张图 `A (195).jpg`（image_id 423）。

处置：**丢弃这 7 条**。1 张图 / 7 个标注，占全集 0.04%，无统计影响。

### 3·3 纠正三：classes.txt 三份 split 顺序不一致

`train/` 与 `val/` 的 `classes.txt` 是 `…, xinfeiao, xinfeitu`；
`test/` 的是 `…, piweitu, xinfeiao, xinfeitu`。
若按 `classes.txt` 的行号去解析 YOLO txt 的类别索引，**最后两类会互换**。

已验证：三份 `*.json` 的 `id → name` 映射**完全一致**，所以
**只从 COCO json 读类别，不要读 classes.txt**。

### 3·4 数据规模

| 项 | 值 |
|---|---|
| 图片总数 | **6,719**（train 5,594 / val 572 / test 553） |
| 标注实例总数 | **18,223**（train 14,677 / val 1,874 / test 1,672） |
| 平均标签数 | **2.71 / 张**（多标签，非单标签） |
| 解压后 | 2.76 GB（图片在 coco/txt/xml 三个文件夹**各存一份**，共 20,157 个图片条目） |
| 标注格式 | COCO json / YOLO txt / VOC xml |

| 类别 | 中文 | 实例数 | 可训性 |

| shenquao | 肾区凹陷 | 495 | 够 |
| xinfeiao | 心肺区凹陷 | 372 | 勉强 |

| shoushe | 瘦小舌 | 285 | 勉强 |

**结论：21 类里只有约 15 类具备训练条件。**
`xinfeitu`(2) / `shenqutu`(2) / `gandantu`(9) / `piweitu`(0) 这四个分区凸起类必须**从输出类别中移除**，
否则它们永远预测不出来，还会拉低整体 micro-F1。

同时 `jiankangshe` 只有 21 个实例，健康舌的识别能力会极弱 —— 这在产品上是硬伤
（用户拍一张正常舌头，模型只会硬套一个病态特征）。缓解办法：把健康舌当"无异常"的默认态，
只有在所有病理类概率都低于阈值时才判为健康，而不是让模型单独学这一类。

## 四、架构决策：分层，不做端到端

```
[舌苔照片] → ResNet18 多标签分类 → "舌形胖大、边有齿痕，苔白滑"
                                        ↓
[白话症状] ────────────────────────→ 拼接文本 → 0.5B → 辨证 + 方剂 + 出处
```

四条理由：

1. **显存**：v2 预训练已占 3.22 GB，端到端要同时跑视觉与语言，激活翻倍必 OOM
2. **没必要**：舌象只有 21 类，是小分类任务，ResNet18（11 M）足够
3. **可验证**：分类器能算每类 F1，出问题能定位是视觉错还是辨证错
4. **可并行**：文本侧 SFT 与视觉侧训练互不阻塞

显存实测：ResNet18 按 batch 8 / 224px + AMP，峰值约 **0.9 GB**，可与预训练共存。

### 4·1 「分类不同的病」的认知纠正

中医舌诊**不是直接对应西医病名**。这 21 类标的是**舌象特征**（舌色、舌形、苔色、苔质 + 五脏分区），
它们是**证型的证据**，不是病名。链路是：

```
照片 → 舌象特征 → 拼进文本 → 辨证 → 方剂
```

不要期望「舌苔照片 → 高血压」这种映射。

### 4·2 词表映射的静默失败（已修，方向先前写反过）

真实数据集用的是**短名**：`shoushe` / `shenquao` / `gandanao` / `piweiao` / `xinfeiao`。
而早期草稿把人脑里更顺的**长名**写成内部规范名：`shouxiaoshe` / `shenquaxian` / `gandanquaxian` / `piweiquaxian`。

> ⚠ 本文件旧版把两边的方向写反了，说明「真实数据集是 shouxiaoshe…」是错的。
> **以 COCO json 的 `categories[].name` 为唯一真源**：里面就是 `shoushe` / `shenquao` 这套短名。

后果：规则表按长名建索引，而 ckpt 存的是短名 → **「瘦小舌」+ 7 个分区类会被静默跳过，且不报任何错**。

修法：规则表保留长名（可读性好），加 `_ALIAS` 把**短名 → 长名**统一翻译后再查表
（`shoushe→shouxiaoshe`、`shenquao→shenquaxian`…）；同时**未覆盖类别显式告警**。
`--demo` 改为做全类别覆盖自检，输出 `未覆盖: 无 ✅`。

**通用纪律：任何「代码里的类别名 ↔ 数据集标签」的映射，必须有覆盖自检。
静默跳过是这类项目最常见的隐性 bug。**

### 4·3 最终 17 类（10-18 清单落地时定稿）

`prepare_tmc_tongue.py` 已改为**从 json 的 `categories` 读类别**，不再写死；四个"凸起"类在
读标注阶段直接进 `DROP` 并计数，不进输出层：

| 丢弃类 | 全量标注数 |
|---|---|
| shenqutu 肾区凸起 | 2 |
| gandantu 肝胆区凸起 | 9 |
| piweitu 脾胃区凸起 | 0 |
| xinfeitu 心肺区凸起 | 2 |

合计 13 条 / 6,719 张图 = 0.19‰。**保留 17 类**（16 病理特征 + `jiankangshe`）。
`jiankangshe` 全量仅 21 条，实际靠"17 维全 0 → 未见异常"兜底，不指望它单独学出来。

**无标签图 191 张默认丢弃**（train 190 / valid 1）：它们不是"健康"，是"没标注"，
保留会被当成负样本，把模型教成"默认健康"。`--keep_empty` 可保留。

清单产物（`tongue-data/manifests/`，由 `--root` 与 `--out` 指定）：

| split | 图数 | 说明 |
|---|---|---|
| train | **5,404** | 原 5,594 − 无标签 190 |
| valid | **571** | 原 572 − 无标签 1 |
| test | **553** | 越界 7 条已丢弃，图数不变 |

共 **6,528 张 / 17 维多标签**，每行带 `names` 字段便于人工核对。

配套修正 `train_tongue_classifier.py`：①标签维度 ≠ 类别数直接 SystemExit（防清单与代码不同源）
②`pos_weight=auto`（neg/pos 夹 [0.3,20]；baitaishe 76% 正 / heitaishe 1.9% 正，不加权必塌）
③ImageNet 权重加载失败显式告警降级随机初始化。
**CPU 干跑已通**（resnet18 11.19M，2 batch），GPU 训练**故意不在预训练期间开** ——
预训练已占 3.57GB、75~76℃（长跑峰值 81℃，熔断线 82℃），再叠一个 CUDA 任务风险大于收益。

## 五、文本侧：证型 → 方剂，统计法失败了三次

### 5·1 第一版：整段共现 → 假覆盖 81.8%

表面 121/148 有方剂，但八个「气虚」开头的证型 **n 全为 2,955、方剂列表完全相同**；
「湿热内蕴证」首推**补中益气汤**（温补治湿热，方向反了）。

根因：古籍单段常 300 字含十几个方名，频次最高的方剂就是最常被提的那个，**与证型无关**。

### 5·2 第二版：句级 + 距离 ≤24 + 治法动词 → 方向对，但仍塌缩

Top1 方剂语义正确（气虚→补中益气汤 341、血虚→四物汤 243、湿热→龙胆泻肝汤 68），
但「气虚不摄 / 气虚痰结 / 气虚血溢」n 仍全为 904 ——
因为证型名里的「不摄」「痰结」「瘀滞」不在词表，被静默丢弃，退化成只查「气虚」。

### 5·3 第三版：拆 病位 × 病性 两轴 + lift 基点率校正

| 证型 | 按绝对数 Top1 | 按 lift Top1 | 谁对 |
|---|---|---|---|
| 下焦·湿热 | 补中益气汤 9 ❌ | **二妙散 ×124 / 龙胆泻肝汤 ×26** ✅ | lift |
| 全身·血瘀 | 失笑散 55 ✅ | 失笑散 ×59 ✅ | 一致 |
| 全身·两虚 | 十全大补汤 63 ✅ | 十全大补汤 ×10 ✅ | 一致 |
| 肾·虚 | 六味地黄丸 45 ✅ | 暖肝煎 ×81（**n=3**）❌ | **都不稳** |

三个致命问题：

1. **组合证抽不出来**：气虚血瘀 8,303 条（占 17%），古籍句 **0 命中**（要求两轴同句太严）
2. **小样本 lift 极不稳定**：3 句就能 ×81
3. **补中益气汤基点率 1,937 次**，几乎污染所有证型

**结论：统计只能产出候选，不能直接当处方表。**

### 5·4 最终产出：人工校订的证型表

`tcm-llm/data/syndrome_table.json`：**35 个证型，按教材体系人工校订**，
覆盖 48,665 条医案中的 **43,383 条 = 89.1%**。

每条字段：证型 / 治法 / 首选方 / 组成 / 出处 / 备选方 / 注意事项，**一律不给克数**。

文件 `_meta` 中显式标注：**出处未逐条回查原书，对外交付前须人工抽检。**
这条不能删 —— 它是这份数据唯一的诚实边界。

## 六、白话化：先量，别先写

`scripts/build_colloquial_stats.py`（48,665 条医案）实测：

| 指标 | 值 |
|---|---|
| 子句总数 | 1,328,966 |
| 每条子句数 | 均 **23.5**，中位 20，最长 226 |
| 套话占比 | **10.4%** |
| 舌脉句占比 | **3.7%** |
| ORAL_MAP 至少命中一条 | 95.7%（**弱指标，不能当改写可行依据**） |

高频「症状」其实多是**阴性陈述**，患者不会这么说：

| 短语 | 出现次数 |
|---|---|
| 无粘液便 | 6,901 |
| 遂来本院求治 | 5,429 |
| 未予治疗 | 4,997 |
| 无咳嗽咳痰 | 4,620 |
| 无视物旋转 | 4,525 |

**处置：这类必须整类剔除，不是做词语替换。** 否则会产出「我没有粘液便」这种不像人话的句子。

另：科室严重不均 —— 肛肠科一个科室约占 1/6（「肛内肿物脱出」7,603 条）。
直接训会做出一个只会看痔疮的模型，**必须按证型配平**。

### 7·1 关于「真多模态」的判断

技术可行：ViT-Tiny(5.7 M) + 线性投影接 embed，参数 524 M → 530 M（+1.1%），
推理显存 +0.2~0.3 GB，冻结 LLM 只训视觉部分在 6 GB 卡跑得动。

**但数据侧不可行**：公开中医舌象数据集规模仅数千张，标注只到「淡白舌 / 黄腻苔」粗类，
**没有任何数据集带「图片 → 证型 → 方剂」完整链路**。医疗图像隐私敏感，拿不到真实配对。

→ 结论：**外挂视觉，不做端到端多模态。**
用成熟视觉模型把照片描述成文本，再喂给语言模型，准确率更高、不占训练预算。
等有配图数据再谈真多模态。
