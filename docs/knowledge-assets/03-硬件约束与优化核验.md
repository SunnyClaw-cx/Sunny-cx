# 03 · 硬件约束与优化核验

> 场景：**GTX 1060 6GB（GP106 / sm_61）** —— 2016 年 Pascal 消费级卡。
> 本文回答一个尖锐问题：**网上流传的 LLM 训练优化清单，在这张卡上有几条能用？**
> 答案：**12 条里 0 条可用**。全部为真机实测，非推断。

---

## 一、硬件事实（实测）

| 项 | 值 |
|---|---|
| GPU | GTX 1060（GP106） |
| 显存 | **6144 MiB** |
| 计算能力 | **sm_61** |
| FP32 算力 | ~4.375 TFLOPS（cuBLAS 实测 1.307 TFLOPS 小矩阵） |
| **FP16 算力** | **68.36 GFLOPS = FP32 的 1/64** |
| bf16 支持 | **不支持** |
| FlashAttention | 不支持 |
| CPU | i7-8750H |
| RAM | 15.9 GB |
| OS | Windows 11 |

### 为什么 FP16 只有 1/64（关键冷知识）

Pascal **消费级**芯片（GP104/106）把 FP16 通路**阉割到 1/64 速率**
（专业卡 GP100 才是 1/2）。
这与常见的"Volta/Turing 的 FP16 不完美"说法**方向完全相反** ——
在这张卡上，**FP16 比 FP32 还慢**。

## 二、12 条优化建议逐条核验（全部否证）

| # | 建议 | 实测证据 | 判定 |
|---|---|---|---|
| 1 | 开 FP16/BF16 混合精度（提速 2-3 倍） | cuBLAS 实测 **fp16 1.429 vs fp32 1.307 TFLOPS → 仅 +9%**；bf16 **-38%**（`1.0+0.001` 在 bf16 下 = 1.0，是残缺实现） | **前提错误** |
| 2 | torch.compile 提速 20~30% | `backend='inductor'` **直接报错**：`Found NVIDIA GeForce GTX 1060 which is too old to be supported by the triton GPU compiler` | **不可用** |
| 3 | 灵核 Liger Kernel GQA 算子 | Liger 是 **Triton 内核库**，本机 triton **ModuleNotFoundError**，且 sm_61 被 triton 拒绝 | **不可用** |
| 4 | 替换高性能 GQA 注意力（FA2/eff） | `sdpa_kernel([FLASH])` → `RuntimeError: No available kernel`；`[EFFICIENT]` 同样失败 | **只能走 math 后端** |
| 5 | INT8 权重量化训 0.5B | 量化是**推理**手段；训练需连续梯度更新，8bit 权重破坏梯度 | **概念错误** |
| 6 | 轻量上下文并行 | 需多 GPU 跨设备通信。本机 **1 张卡** | **不可用** |
| 7 | batch 翻倍省时间 | GPU 利用率长期 **97%**、均值 90.9% → 算力已饱和；tiny 实测 2×8 vs 4×4 吞吐仅差 **5.5%** | **无收益** |
| 8 | num_workers=4 + pin_memory | 数据加载实测仅 **3~7 ms/batch**，占 17.4s/step 的 **0.2%** | **非瓶颈** |
| 9 | 二进制语料（.bin/.arrow） | 同上，数据加载不是瓶颈，改格式收益 ≈ 0 | **非瓶颈** |
| 10 | 启用梯度检查点 | **已在跑**（`trainer.py` + bat 参数） | 已在跑 |
| 11 | 8bit AdamW | **已在跑**（日志 `[optim] 使用 bitsandbytes 8-bit AdamW`） | 已在跑 |
| 12 | warmup + 余弦退火 / 梯度裁剪 | **已在跑**（warmup 200 + cosine；clip 1.0） | 已在跑 |

### 结论分布
- **物理不可能**：6 条（1、2、3、4、5、6）
- **无收益/非瓶颈**：3 条（7、8、9）
- **已在跑**：3 条（10、11、12）

## 三、17.4 s/step 的真实构成（把"落差"查清楚）

早期 bench 报 **13.0 s/step（630 tok/s）**，正式训练实测 **17.4 s/step（471 tok/s）**。
差值不是 bug，逐项拆解如下：

| 项 | 耗时 | 占比 |
|---|---|---|
| `weight_drift()` 每步 GPU→CPU 搬 186MB | ~0.40 s | 2.3% |
| `nvidia-smi` 查询（thermal 节流后） | ~0.30 s | 1.7% |
| **梯度检查点开销** | **~4.4 s** | **~25%** |
| 其余为正常算力 | — | — |

**梯度检查点的代价实测**：tiny 对照 gck ON **1065** vs OFF **1258 tok/s** → **-15~18%**。
`13.0 × 1.33 ≈ 17.3 ≈ 实测 17.4` —— 完全吻合。

> **即「630 tok/s」是未开 gck 的数字；正式训练开了 gck（保 6GB 不 OOM）→ 471 tok/s 是正常代价，不是 bug。**

## 四、温度实测（本卡散热结论，有实用价值）

| 项 | 实测 |
|---|---|
| 短时满载温度 | **73~74℃**（87~98% 利用率下，数分钟级采样） |
| **长跑稳态峰值** | **81℃**（24.8h 连续训练，熔断计数 0 次） |
| 热降频位 | `clocks_throttle_reasons.active` 仅 `0x1`(Idle)/`0x4`(SwPowerCap)，**`0x20/0x40` 从未触发** |
| 功耗 | 57~76 W（上限 **78W**，已撞功耗墙） |
| 风扇 | `[N/A]` —— **GTX 1060 不支持风扇控制**，"调高转速"物理做不到 |

> ⚠ **重要修正（2026-10-18 实测证伪）**：早期结论"满载仅 73~74℃、离 82℃ 尚远"
> **只在短时采样下成立**。24.8h 连续训练的真实峰值是 **81℃，距 82℃ 熔断线仅 1℃**。
> 机理：机箱内热堆积是**小时级**过程，数分钟 bench 测不到稳态。
> **结论翻转**：温度熔断不是"冗余保险"，而是**真实逼近中的保护**——
> 夏季室温升高或散热积灰后，有实际触发可能。不要因为"从没触发过"就拆掉它。

### ⚠ 关键踩坑：bit mask 判定必须用真实读数验证

第一版把 `0x4` **误当热降频**，实际 `0x4 = SwPowerCap`（功耗上限）。
GTX 1060 是 78W 卡，**空闲 43℃ 时 `0x4` 也一直置位** →
会让训练在完全正常温度下**反复熔断、根本起不来**。

热降频实为 **0x20 SwThermalSlowdown / 0x40 HwThermalSlowdown**。

> **教训**：读硬件寄存器/位掩码，**必须打印真实读数对照**，不能凭位序猜。

### 熔断参数
```
pause_c = 82℃（持续 20s） / resume_c = 74℃ / poll_sec = 5 / check_every_sec = 3
```
- **双阈值滞回**（82/74）：单阈值会在边界反复穿越 → 训练抽风式启停
- **失败安全**：读不到温度（无 nvidia-smi / 非 CUDA）→ **自动停用熔断，绝不拦训练**
- 实测：短时满载 73~74℃；**24.8h 长跑峰值 81℃，熔断 0 次**（余量仅 1℃，见上方修正）

## 六、一句话总结

> **在这张卡上，"优化"的空间已经被硬件封死了。**
> 唯一真正有效的两条是：**序列打包**（省 82% 无效算力）和
> **权重 fp16 驻留**（把不可能的 OOM 变成可能）。
> 其余所谓优化，要么物理不可用，要么本来就在跑，要么收益为 0。
