### 早停法的量纲陷阱（已修复）

西瓜书说"验证误差升高则停"，但工程实现有个坑：

```python
# ❌ 错误：比较步数差。val_interval=500 时 patience=5 永远只等于 1 次验证
if step - best_step >= patience:

# ✅ 正确：按验证次数计数
if val_loss < best_val - min_delta:
    bad_count = 0
else:
    bad_count += 1
    if bad_count >= patience: stop()
```

## 四、关键工程修复（实测踩坑记录）

### 1. 权重驻留精度决定 OOM 与否（P0）

`model.to(device)` 默认保持 fp32，则 524M × 4 B = **2.10 GiB 权重**，
梯度同量级，合计 4.2 GiB，在 6GB 卡上首次 embedding 查表即 OOM。

改 `model.to(device=device, dtype=torch.float16)` → 权重 0.98 GiB。
**这是 num_params × 4 vs × 2 的差别，直接决定成败。**

### 2. fp16 权重与 GradScaler 不兼容（P0）

torch 的 `GradScaler` 在 `unscale_` 时会校验梯度 dtype，
fp16 梯度直接抛 `ValueError("Attempting to unscale FP16 gradients.")`。

故实现 `StaticScaler`（固定系数 S=1024，2 的幂避免舍入误差）：

```
forward : loss' = loss · S
backward: grad' = grad · S      ← 把 fp16 下溢的小梯度抬到可表示范围
update  : grad  = grad' / S     ← 还原真实量级后再 clip / step
```

### 3. fp16 梯度裁剪会静默清零梯度（P0）

`torch.nn.utils.clip_grad_norm_` 在梯度自身精度下求范数。
fp16 下 `grad.pow(2)` 在 |grad|>~256 时上溢为 inf，总范数变 inf，
裁剪系数退化为 0，**梯度被整体清零**——表现为 loss 突然卡住，且无任何报错。

故实现 `clip_grad_norm_safe()`，统一在 **fp32** 下累加范数。

### 4. RoPE 表精度提升会拖垮整条注意力路径

cos/sin 以 fp32 预计算（角度精度需要），若直接与 fp16 的 q 相乘，
类型提升会把整条注意力抬回 fp32，既费显存又失去混合精度意义。
故 `apply_rope` 内按 q 的 dtype 转换 cos/sin。

### 5. 日志块缓冲导致"训练无输出"

stdout 重定向到文件时 Python 默认 4~8KB 块缓冲，日志长时间不落盘。
已加 `sys.stdout.reconfigure(line_buffering=True)`，长跑训练进度必须实时可见。

### 五·B、序列打包（关键效率优化）

实测预训练样本长度分布（4000 条随机采样）：

| 分位 | P10 | P25 | P50 | P75 | P90 | P99 | P100 |
|---|---|---|---|---|---|---|---|
| token | 35 | 41 | **60** | 98 | 183 | 521 | 917 |

均值 **91.7**，中位 **60** —— 样本极短。

| seq_len | 完整容纳 | **填充利用率** |
|---|---|---|
| 128 | 82.7% | 55.2% |
| 512 | 99.0% | **17.6%** ❌ |

**根因**：按单样本 pad 到 512，**82% 算力在计算 padding**，
单 epoch 需 63,663 step × 15.6 s = **11.5 天**。

**解法**：`PackedPretrainDataset` —— 以 eos 为文档分隔符拼接 token 流，
攒满 512 即切出（GPT/LLaMA 标准做法，Krell et al. 2021）。

实测效果：
- padding 占比 **80.0% → 0.00%**
- 每 epoch step 数 **63,663 → 11,946**（**5.3 倍**）
- 单 epoch **11.5 天 → 约 2.2 天**

> 注意：**验证集不做打包**，保持单样本 pad 口径，
> 否则 val_loss 与 train_loss 不同源、失去可比性（西瓜书 5.3 早停法要求验证误差可比）。

## 六、数据账（关键约束）

实测（全量精确统计，非采样）：

| 数据集 | 条数 | 字符 | tokens |
|---|---|---|---|
| 预训练 train | 1,018,615 | 1.181 亿 | **0.945 亿** |
| 预训练 val | 53,705 | 0.066 亿 | 0.054 亿 |

**Chinchilla 最优数据/参数比 = 20**，0.5B(524M) 需要约 **104 亿 tokens**。
当前 0.945 亿 → 数据/参数比 **1.8**，缺口 **11 倍**。

这是**物理上限**：中医古籍含海外普本、辑佚本共约 4000~5000 种，
全部数字化也仅约 2~3 亿 tokens。故纯中医语料**喂不饱** 0.5B。

**结论**：0.5B 自研栈在工程上完全跑通（这是事实），但在纯中医古籍上
会严重欠训练。三条出路见 `docs/参数量0.5B可行性评估.md`。
